ANNOTINDER-CLIENT DESIGN PLAN
=============================
Status: draft v3 (all v2 open questions resolved by Kasper; codebook data
model revised accordingly). Answers are recorded inline as [ANSWER]/[NOTE]
blocks for history; resolutions are also folded into the main text and
summarized in §10.


0. VISION (recap)
-----------------
Annocate/Annotinder is an annotation + survey tool for researchers. The previous
NextJS fullstack app ("old/") is being split into:
  - annotinder-client: a framework-agnostic, purely client-side React app (this repo)
  - one or more server backends (R, Python, Node, ...), which only need to satisfy a
    documented API contract. We are not building "the" production server here.

Guiding principle for every decision below: the client should be able to run against
ANY backend that implements the contract, so nothing may leak into the client that
assumes a specific server implementation (no DB types, no NextJS API-route helpers,
no server-side auth libraries baked in).


1. REPOSITORY / PACKAGE STRUCTURE
----------------------------------
Decision: use a pnpm workspace monorepo, in the root of this repo (not a separate
repo per package). Rationale: contracts must be shared, type-safe, and versioned
together with the client and the mock server during active development; splitting
repos now would slow iteration and can be done later if/when we publish separately.

  /package.json              workspace root (pnpm-workspace.yaml), shared tooling config
  /packages/contracts/       zod schemas = single source of truth for the API.
                              - exports TS types + zod schemas (for client & mock-server)
                              - build script exports JSON Schema (zod-to-json-schema)
                                and/or OpenAPI (zod-to-openapi) for non-JS server authors
                              - zero React/Node-specific dependencies
  /packages/client/          the Vite + React app (what most users will eventually
                              install/embed). Depends on @annotinder/contracts.
  /packages/mock-server/     small Node server (reference implementation + local dev).
                              SQLite-backed, trivially resettable. Depends on contracts.
  /old/                      legacy NextJS app, kept only as reference during porting.
                              Will be deleted once migration is complete.

Packages are namespaced e.g. `@annotinder/client`, `@annotinder/contracts`,
`@annotinder/mock-server`, so `client` can later be extracted/published to npm on its
own without touching import paths.

2. DATA MODEL (replacing projects/jobsets/jobs)          [REVISED per answers]
------------------------------------------------
Drop "projects" entirely. The only top-level entity is a "job".

  job
    - id, name, created, archived/deployed flag
    - job users: people who manage the job (NOT the same thing as coders — see
      below), each with a role: ADMIN | WRITE | READ. Managed as a full-replace
      list (`PUT /job/:id/users`), consistent with the whole-resource philosophy.
    - unitsets[]          named, ordered selections of units (see `unitset`
      below) — replaces the old jobSets/jobSetUnits concept, but scoped to
      "which units, in what order" rather than "which coders see what" (coder
      assignment now happens via codebook branching/auto-variables instead,
      see `codebook` below).
    - codebooks[]         (multiple allowed; immutable once used — see below)

  unitset
    - belongs to a job; { id, name, unit ids in order (or a rule such as
      "random order") }
    - referenced by a codebook's "unit loop" item (see below) to determine
      which units that loop iterates over, and in what order. A job can have
      multiple unitsets (e.g. to assign different unit sequences to different
      experimental conditions, or a practice set vs. a main set).
    - units themselves stay a flat, job-scoped, immutable-once-used list, same
      as before; a unitset just orders/selects from that list rather than
      duplicating unit content.

  codebook                                                [REDESIGNED]
    - belongs to a job; stored as ONE json blob (full document, no partial
      updates — matches §3).
    - NOT a DAG of nodes anymore. It is a FLAT ARRAY of items, each with a
      dotted-decimal `position` (e.g. "2", "4", "4.1", "4.2", "4.2.1") that
      encodes parent/child nesting purely through the position value (item
      "4.1" is a child of item "4"). Simpler to store/diff/validate than a
      normalized tree, at the cost of some flexibility (e.g. reordering means
      recomputing positions — see Phase 5 note on editor implementation).
    - Item types:
        - user variable: any question/info-block/screen-out/"auto" variable
          (auto variables can take a random value, or a value from a URL
          param — this is now how "experimental condition assignment"
          works, e.g. an auto variable `experimental_group`; researchers can
          later also assign a specific coder's value for such a variable
          explicitly). Leaf node — cannot have children.
        - unit loop: like a `for unit in unitset`. References one of the
          job's `unitsets`, and carries loop-level settings (layout to use,
          whether unit order is randomized per-coder, etc). MUST have
          children (meaningless without them). E.g. a unit loop at position
          "4" has its unit variables at "4.1", "4.2", ...
        - condition: like `if <expression>:` — determines whether its
          children are shown to the coder. Can appear anywhere in the tree.
        - unit variable: like a user variable, but only valid/meaningful
          inside a unit loop (may allow additional annotation types, e.g.
          span annotations, that don't make sense outside a unit context).
    - Nesting rules (validated client-side, ported/rewritten from
      `treeFunctions.ts` for the new positional model): variables (user or
      unit) are always leaves; user variables cannot appear inside a unit
      loop; unit variables MUST appear inside a unit loop; conditions may
      appear anywhere; unit loops cannot be nested inside another unit loop.
      Moving a variable across the user/unit boundary (i.e. in/out of a unit
      loop) is intentionally NOT supported — treated as delete + recreate,
      since the two variable kinds may carry different, non-transferable
      settings.
    - Once referenced by any coder progress/variable, a codebook becomes
      immutable and undeletable; editing creates a new codebook record
      instead (client must support a "duplicate as new codebook" workflow).

  unit
    - belongs to a job, has externalId + data (unchanged from old design).
    - has a `variables` json field, keyed by coder id, holding that coder's
      unit-level variables for this unit:
        unit.variables = { [coderId]: { [variableName]: VariableValue } }
    - once a unit has recorded variables for ANY coder, or is referenced by a
      deployed codebook run, the unit content itself becomes immutable (data
      can no longer change) — new units must be created instead.

  coder
    - belongs to a job (job-scoped identity, distinct from "job users" above —
      a coder is someone doing the annotation task via an invite/access link,
      not someone managing the job).
    - has a `variables` json field for coder-level (global/survey) variables:
        coder.variables = { [variableName]: VariableValue }
    - has session/progress bookkeeping (current unit-loop/unit index, done
      flags per unitset — see §3 for the still-open questions on exactly what
      shape this takes).

Rename throughout the codebase: "annotation(s)" -> "variable(s)" wherever we mean
the recorded coder input. Keep "codebook variable" naming for the *definition*.

This removes: `projects`, `managers`, `jobSets`/`jobSetUnits` as coder-facing
concepts (replaced by `unitsets` as a pure unit-ordering concept, with coder
assignment moved into codebook auto-variables/conditions), `invitations` as a
separate table (invitations become simple job-scoped access links, see §5),
`annotatorSession`/`annotatorUnits`/`variableAnnotations` as normalized tables
(replaced by the json fields above), and `codebookNodes` as a normalized DAG
table (replaced by the flat positional array inside the codebook json blob).

RESOLVED: package scope confirmed as `@annotinder/*` (was open question in §1).


3. API CONTRACT (packages/contracts)
--------------------------------------
Design goals: minimal endpoints, coarse-grained (whole-resource) reads/writes,
stateless-friendly (so a server can be implemented in ~an afternoon in any
language), and reproducibility guarantees baked into the shapes.

Endpoints (all scoped under a job; a server may expose one job per deployment,
or route by jobId — the client should not assume which):

  POST   /job                  create a job
  GET    /job/:id               job metadata
  PUT    /job/:id                update job metadata (full replace)
  DELETE /job/:id                delete a job
  GET    /job/:id/users          list job users (manager-only)
  PUT    /job/:id/users          replace the full list of job users + roles
                                 (ADMIN | WRITE | READ) — whole-resource, like
                                 the codebook endpoints.

  GET    /codebook           list codebook (metadata only: id, name, created, immutable)
  GET    /codebook/:id        full codebook document
  POST   /codebook            create a new codebook (full document)
  PUT    /codebook/:id        replace a codebook IN FULL (fails if immutable)
  DELETE /codebook/:id        delete a codebook (fails if immutable/in use)

  GET    /units               list unit metadata (id, externalId, hash) — for sync
  GET    /units/:id            full unit (fails/redacts if not permitted)
  POST   /units               bulk create units
  DELETE /units/:id            delete a unit (fails if immutable/in use)
  GET    /unitsets              list unitsets (id, name, unit ordering/rule)
  POST   /unitsets              create a unitset
  PUT    /unitsets/:id           replace a unitset in full
  DELETE /unitsets/:id           delete a unitset (fails if referenced by a
                                 unit loop in an in-use codebook)

  GET    /session              resolve the current coder's session (auth token in,
                                coder id/progress/codebook reference out)
  GET    /unitset/:setname/next  get the next unit within a given unitset (or
                                `_` for "the job's only/default unitset") +
                                this coder's existing variables for it
                                (replaces old getUnit; setname-scoped because a
                                codebook can now have multiple unit loops)
  POST   /variables/unit       upsert this coder's variables for a given unit
                                (id = jobId+coderId+unitId+variableName, full
                                replace of that unit's variable object — no partial
                                merge logic needed server-side)
  POST   /variables/coder      upsert this coder's job-level (non-unit) variables

  GET    /coders                (manager-only) list coders + progress in a job
  POST   /coders/invite          create an invitation/access link

3a. OPEN DESIGN POINT — unit delivery & resumable progress (not yet resolved)
Raised in Kasper's note; needs a decision before/while implementing Phase 2,
but not before Phase 1 contract scaffolding since it mainly affects `/session`
and `/unitset/:setname/next` response shapes, not the rest of the contract.

Problem: a coder must be able to log back in and resume (incl. going back to
previous units), which requires the server to convey progress/order somehow.
Three options considered, each with tradeoffs:
  (A) `/session` returns, per unitset, the list of done unit ids (ordered by
      the coder's own annotation `created` timestamps) — client derives "next"
      itself and can go back by index. Cheap for small/medium unit counts,
      does NOT support crowd-coding (global assignment queue) later.
  (B) `/session` returns full annotation history — same idea, larger payload,
      redundant with data already needed elsewhere.
  (C) `/session` (or a dedicated endpoint) returns the FULL unit queue for the
      coder up front (optionally client-randomized) — simplest for the
      client, but doesn't scale to very large unit counts and is fundamentally
      incompatible with crowd-coding (where assignment depends on a live,
      shared, cross-coder queue and can't be precomputed at session start).

Decision for MVP (Phases 2-4): implement option (A) — done-unit-id list per
unitset in `/session`, plus `/unitset/:setname/next` for forward progress and
plain by-index lookups for "going back". This is the simplest option that
still keeps the door open for crowd-coding later (which would instead require
`/unitset/:setname/next` to consult a server-side global queue rather than a
per-coder precomputed list — a server-implementation concern, not a contract
shape change). Revisit batching/pagination if/when unit counts get large
enough for (A)'s payload to matter (flag as a Phase 6+ concern, not a v1
blocker).

No more granular `codebookNodes/:id` CRUD (that was the "partial, efficient
update" model we are explicitly dropping per the brief). The client is
responsible for building/validating the *entire* codebook tree locally (zod
schema + tree-shape validation, ported from `functions/treeFunctions.ts`) before
ever calling PUT/POST — the server only needs structural + auth validation.

Contracts package exports, for every endpoint: a zod request schema, a zod
response schema, and a small typed helper (path + method) — so both the mock
server and any typed client wrapper can import the same definitions. Also
exports a generated JSON Schema bundle (via zod-to-json-schema) so non-TS
server implementers (R/Python) have a language-agnostic spec to code against,
and (optionally) an OpenAPI document via zod-to-openapi for interactive docs
(old app/api/page.tsx already used swagger-ui-react for this — can reuse the
idea by serving the generated OpenAPI JSON from the mock-server's docs route).


4. AUTH / SESSION MODEL
--------------------------
The client must not hard-depend on Middlecat (that was a NextAuth-adjacent,
server-side-session-oriented model). Instead:

  - The client only needs an opaque bearer token per job (however obtained —
    invitation link, Middlecat, a magic link, HTTP basic, whatever). It is
    passed to every request via a pluggable `JobServer`-like transport
    (interface already exists in old code as `JobServer`; port + simplify it).
  - For the "coder session" itself (no login required, anonymous/invite-link
    based annotation, as used heavily today), the plan is to have the server
    issue a **signed (HMAC), self-contained session token** after job creation,
    so the server does not need to keep session state in a DB at all — it can
    validate + read coder id/progress directly off the token signature. This
    was flagged by Kasper as "discuss later"; for now the mock-server can do
    this simply (sign a JSON payload with a server secret), and the contract
    package should model the token as an opaque string so alternate server
    implementations can choose their own session strategy as long as they
    return/accept the same opaque token shape.

[RESOLVED — deferred to Phase 6, design documented now] Kasper: let's wait
with implementing HMAC signing for now, but here's the intended design so it
can be accounted for in the contract/data-model shapes in the meantime:
  - The server holds one global salt used for signing.
  - When a codebook is created/updated, the server signs the allowed-value
    "tokens" for each variable individually, e.g. for a `gender` variable with
    values male/female/other, each value gets its own signature:
        HMAC(codebook_id, variable, validation_rule, value, position)
    so the server can later validate a submitted answer against this
    signature WITHOUT needing to fetch/parse the codebook at all.
  - `validation_rule` controls which parts feed the hash / what the coder
    actually submits:
      - `v` = "validate exact value": the value itself is part of the hash,
        and the coder submits the plain value + the precomputed signature,
        e.g. submitting `female.v.<hash>`.
      - `i3:6` = "integer in range 3..6": value is NOT part of the hash (it's
        NULL/omitted since any integer in range is valid); the validation
        rule string itself is embedded in what the coder submits, e.g.
        `(female,v,hash)`-style tuples, or `i3:6.<hash>` for a numeric answer.
  - Net effect: the mock-server (and any real server) can stay fully
    stateless about codebook contents at answer-submission time — it only
    needs the global salt to re-derive and compare the HMAC, rather than
    re-fetching/re-validating the whole codebook document per submission.
  - Implication for the contract: variable value payloads posted via
    `POST /variables/unit` / `POST /variables/coder` need a field to carry
    this signature/validation-rule alongside the value (exact shape to be
    finalized in Phase 6, but contracts should reserve room for it now,
    e.g. an optional `proof` string on the variable-value schema, so we don't
    need a breaking contract change later).


5. CLIENT ARCHITECTURE
--------------------------
Keep the current conceptual pieces, ported and simplified:

  - `JobManager` (classes/JobManager.ts) — the central client-side state
    machine driving navigation/progress/annotation-library. Port largely as-is;
    update call sites to the new contract endpoints/shapes (rename
    annotations -> variables throughout; drop phase-token/session-token
    plumbing that existed only to support the old normalized DB tables).
  - `functions/jobManagerState/*` — progress/annotation-library computation.
    Port with the variable renaming; should get simpler since unit variables
    are now a flat per-coder json blob instead of normalized rows.
  - `functions/treeFunctions.ts` — codebook shape/nesting validation logic.
    Needs a substantial rewrite (not a straight port) for the new flat/
    positional codebook model (§2): position-string parsing/ordering,
    parent/child derivation from position values, and the new item-type
    nesting rules (user variable / unit loop / condition / unit variable).
    This becomes MORE important than before, since the client now owns full
    codebook validation before submission (server does only structural/auth
    checks).
  - `components/AnnotationInterface/*`, `components/Document/*` — the actual
    annotation UI (span/relation/select/scale/etc question types). Port with
    minimal changes; these are the most reusable, backend-agnostic pieces.
  - Codebook builder UI (`app/projects/[projectId]/jobs/[jobId]/codebook/*`)
    — port, adapted to the job-scoped routes (no projectId) and to the new
    "edit mode" requirement described next.
  - NEW: explicit edit-mode + dirty-state guard for the codebook editor. Since
    there is no more incremental save, the editor must:
      1. Load the codebook into local editable state on "Edit" click.
      2. Track a dirty flag on any change.
      3. Block route navigation / tab close while dirty (confirm dialog:
         discard / save / cancel), using a router-level guard + a
         `beforeunload` handler.
      4. On Save, PUT the entire document; on success, exit edit mode.
    This is a reusable hook, e.g. `useEditableResource<T>()`, since the same
    pattern will likely apply to units and other whole-resource forms.

State/data libraries: keep React Query (server cache + mutations fit the new
coarse REST endpoints very well), Zod (validation + type inference, and now
also doubles as the API contract format), React Hook Form, ShadCN + Tailwind
for UI. Drop anything NextJS-specific (app router, server actions, next/image,
next-themes can stay or be replaced by a plain theme approach since we no
longer have SSR).

Styled-components is used in ~18 files, mostly for dynamic per-token/span
color styling in the Document renderer. Recommend KEEPING it for that narrow
use case (computed inline styles based on annotation color don't map cleanly
to static Tailwind classes) but auditing during migration whether any of the
18 usages can be trivially converted to Tailwind + CSS variables to reduce the
dependency footprint. Not a blocker for v1.

Testing: switch from Jest (NextJS/babel-oriented) to Vitest, since we're on
Vite. Keep React Testing Library.


6. MOCK SERVER (packages/mock-server)
----------------------------------------
  - Minimal Node server (recommend a lightweight framework — e.g. Hono or
    plain `node:http`/Express — pick whichever keeps deps minimal; Hono is a
    good fit given it's fetch-standard and works well with zod validation
    middleware).
  - SQLite via the built-in `node:sqlite` (Node >= 22, see resolved decision
    below) as the storage, mirroring the simplified schema in §2 (jobs,
    codebooks, units, coders — each with the json blob columns described
    above).
  - Fully resettable: a single script/endpoint to drop + recreate + optionally
    seed the DB, so it can be reset between test runs or demo sessions.
  - Implements every endpoint in §3 using the same zod schemas from
    `@annotinder/contracts` for request validation and response shaping —
    this makes it double as executable documentation of the contract.
  - Serves the generated OpenAPI/JSON Schema docs at a `/docs` route for
    convenience (reusing the swagger-ui-react idea from the old app, or a
    lighter alternative like Scalar).

[RESOLVED] Node >= 22, using the built-in `node:sqlite` (no `better-sqlite3`
dependency needed).


7. DEPENDENCY / VERSION STRATEGY                              [RESOLVED]
------------------------------------
Decision: pin to the same major versions as `old/` while porting (React 19,
Zod 3, Tailwind 3, current TanStack Query/Table, etc.), then do a dedicated
version-upgrade pass in a later phase once the new data model/contracts have
stabilized. This matches Kasper's stated preference, and also reduces the
number of simultaneously-changing variables while ported code is being
adapted to the new data model — easier to tell whether a bug came from the
data-model change or from a library upgrade. Add a dedicated step for this
(see Phase 6.5 below) rather than folding it into Phase 1.


8. STEPWISE EXECUTION PLAN
------------------------------
Phase 0 — Workspace scaffolding
  0.1 Set up pnpm workspace (pnpm-workspace.yaml, root package.json, shared
      tsconfig base, shared eslint/prettier config).
  0.2 Scaffold packages/client with Vite + React + TS template. Set up the
      Vite config with both a standalone-app entry (for local dev against the
      mock-server) and a library-mode build target (components/hooks exported
      for consumption inside another host React app — see Phase 7), so the
      "importable as a plugin" requirement doesn't require reworking the
      build later.
  0.3 Scaffold packages/contracts as a plain TS package (no bundler needed
      beyond `tsc`, or `tsup` if we want dual ESM/CJS output for the mock
      server + future non-Vite consumers).
  0.4 Scaffold packages/mock-server as a plain Node/TS package.
  0.5 Wire up root scripts: `dev` (run client + mock-server concurrently),
      `build`, `test`, `lint`.

Phase 1 — Contracts first
  1.1 Port zod schemas for codebook nodes, units, variables/annotations from
      old/src/app/api/**/schemas.ts, adapted to the simplified endpoint list
      in §3 (drop project/jobset-specific schemas).
  1.2 Define the simplified DB-shaped types (job, codebook, unit, coder) as
      zod schemas — these ARE the wire format now, no separate DB layer.
  1.3 Add JSON Schema (+ optionally OpenAPI) generation script/output.
  1.4 Write a short CONTRACTS.md documenting each endpoint (method, path,
      request/response schema reference, auth requirement, idempotency /
      immutability notes).

Phase 2 — Mock server MVP
  2.1 SQLite schema matching §2 (jobs, codebooks, units, coders tables with
      json columns).
  2.2 Implement all §3 endpoints using contracts package schemas for
      validation.
  2.3 Seed script + reset script; a couple of example jobs/codebooks/units
      for local dev and for the client's own dev fixtures.
  2.4 Minimal unsigned/dev-mode session handling (defer HMAC signing to
      Phase 6).

Phase 3 — Client core plumbing
  3.1 Port `JobServer` interface + a `HttpJobServer` implementation that talks
      to the mock server via the new endpoints (replacing `JobServerDesign`/
      `MockServer.ts` class-based mocking with a real HTTP mock-server; keep
      the "design/offline" JobServer variant if useful for Storybook-like
      isolated component development).
  3.2 Port `JobManager` + `functions/jobManagerState/*`, renaming
      annotations -> variables, and simplifying around the new flat
      per-coder-per-unit variable storage (no more phase/session tokens).
  3.3 Rewrite `functions/treeFunctions.ts` for the new positional codebook
      model (§2) — this is now the client's sole source of truth for
      codebook validity.
  3.4 Get one full annotation flow working end-to-end against the mock
      server: session -> get unit -> answer a question -> post variables ->
      next unit -> finished screen.

Phase 4 — Annotation UI port
  4.1 Port `components/AnnotationInterface/*` (question forms, answer fields:
      annotinder/confirm/scale/searchCode/selectCode). [DONE]
  4.2 Port `components/Document/*` (span/relation annotation rendering,
      token/text/image/markdown rendering). [PARTIALLY DONE: text/markdown/
      image field rendering shipped; span/relation rendering BLOCKED on a
      design pass -- see §11]
  4.3 Port supporting `functions/*` (tokens, relations, rendering, swipe
      control, etc.) as needed by the above. [BLOCKED on §11]
  4.4 Visual/UX parity pass against the old app for the core annotation
      experience.

Phase 5 — Codebook + job management UI port
  5.1 Job list / job creation (replacing project+job nesting with a flat job
      list).
  5.2 Codebook editor: port `CodebookNodes`/`CodebookNodeForm`/
      `CodebookPreview`/tree-manipulation UI, wired to whole-document
      GET/PUT/POST/DELETE, with the new edit-mode + dirty-guard (§5).
  5.3 Multi-codebook support in the UI (list of codebooks per job, "duplicate
      as new" flow instead of edit-in-place once immutable).
  5.4 Units management UI (upload/list/delete units), respecting immutability
      once used.
  5.5 Coders/progress overview + invitation link creation.

Phase 6 — Hardening
  6.1 Design + implement the HMAC-signed session-token scheme (client-side
      support is likely a no-op since tokens stay opaque; mainly a
      mock-server concern, but document it clearly in CONTRACTS.md so other
      server authors can implement equivalent stateless validation).
  6.2 Immutability enforcement end-to-end (client hides/disables destructive
      actions once a codebook/unit is in use; mock server rejects such
      mutations).
  6.3 Error/edge-case handling pass (network failures, stale dirty-state
      conflicts, invalid codebooks).
  6.4 Test coverage: Vitest unit tests for contracts + jobManagerState logic,
      component tests for the annotation interface, a basic e2e smoke test
      against the mock server (Playwright, optional).
  6.5 Dedicated dependency-upgrade pass: bump React/Zod/TanStack/Tailwind/
      ShadCN etc. to latest, now that the ported code + new data model have
      stabilized (see §7 — pin-then-upgrade decision).

Phase 7 — Packaging                                          [SCOPE CLARIFIED]
  7.1 Structure packages/client so its components/hooks are importable
      directly into a host app's own React tree (e.g. Kasper's separate
      "database tool" wants to use annotinder-client as a plugin/component

  7.2 DO NOT publish packages/contracts or packages/client to npm yet — defer
      until we actually need it consumed externally. Revisit naming/publish
      workflow at that point.
  7.3 Decide fate of `old/` (delete once parity is reached and no longer
      needed as reference).

11. UNIT LAYOUT + ANNOTATION MODE REDESIGN (span/relation)
    [11a/11c RESOLVED + span IMPLEMENTED (2026-09-18); relations still open]
-------------------------------------------------------------------------------
Raised after Phase 4.1/4.2: `@annotinder/contracts`' codebook/layout schemas
currently have NO span or relation field/variable type at all, so
`old/src/components/Document/*` (~2700 lines: token rendering, span
selection, relation arrows) cannot be ported as-is. This section records the
user's own summary of what that old feature did and how it should change,
as a starting point for a fresh design pass (not yet implemented/decided).

11a. What span/relation annotation actually did (old app)
  - Tokenizing: unit text was tokenized (word-level, via the `compromise`
    NLP library) so the coder could select spans of one or more whole words
    and annotate the selected span with a label from a codebook-defined set
    of codes.
  - Relations: two existing spans could be linked together with a relation
    label. Primary use case: identifying "actor" and "issue" spans in a
    text, then drawing a relation between them (e.g. a "position"/stance
    relation) to encode "this actor feels X about this issue."
  - Old app kept a hard separation between "question mode" (the
    AnnotationInterface / QuestionForm flow — user_variable / unit_variable
    style Q&A) and "annotation mode" (the Document/span-relation UI) — two
    distinct interaction modes bolted together, not one integrated flow.

11b. What should change (per user's 2026-09-18 direction)
  - Integration: annotation mode (span/relation) should eventually be
    brought back, but INTEGRATED with the question-form interface rather
    than kept as a wholly separate mode — i.e. a unit_variable of type
    "span"/"relation" should fit into the same JobManager-driven step flow
    as confirm/select_code/scale/etc, not a parallel system.
  - Simplify span mechanics substantially:
      - Drop the tokenization library dependency (no `compromise` or
        equivalent word-tokenizer). No token-index-based offsets.
      - Spans are stored simply as CHARACTER-INDEX offsets into the
        underlying text (e.g. `{start, end}` character positions), not the
        old token-based indexing scheme. The coder-facing selection
        interaction can still be word-oriented (e.g. snapping selection
        to word boundaries) but the *stored/contract* representation
        should be plain character offsets — much simpler than the old
        pipeline.
      - Relations: still "a link between two existing spans with a label",
        mechanism/schema TBD but should follow from the simplified span
        representation.

11c. The other, related open problem: unit layout simplification
  History of the old app's unit layout: started as a single text field ->
  became an array of typed fields (text/image/etc) -> gained a complex grid-
  based arrangement system -> gained markdown fields (XSS-safe rendering,
  with other fields "injected" into the markdown via templating, and
  formerly small JS scripts for logic -- which this redesign now replaces
  with sandboxed JS (QuickJS), see 11d below for how this scripting/
  condition-expression choice evolved and was finalized.

  User's proposal to investigate: collapse the unit layout down to
  supporting JUST ONE markdown field (dropping the separate text/image
  field-array + grid-arrangement system entirely), IF it can be confirmed to
  cover all current needs:
    1. Images: need to confirm markdown rendering can embed images
       adequately (this is normally supported by markdown, likely fine).
    2. Styling control: current approach lets users set arbitrary inline
       CSS per field (React inline-style objects are injection-safe by
       construction). Need to confirm an XSS-safe markdown renderer can
       offer equivalent (or better) per-element styling control -- not
       yet verified whether typical markdown-renderer setups (e.g.
       react-markdown + remark/rehype plugins) support this cleanly.
    3. Annotatable regions: the hardest requirement. Some portion(s) of the
       rendered content need to render as SPECIAL interactive components
       (to support span selection now, and image-region annotation later)
       rather than plain static markdown output. This requires the chosen
       markdown interpreter to support custom component rendering for
       specific injected content (e.g. a custom remark/rehype node type or
       component-override mechanism) -- not yet verified as feasible with
       any specific library.

  This is explicitly flagged as a chunk of work needing its own focused
  design pass (candidate markdown/renderer library evaluation, a concrete
  span/relation contract schema proposal, and an annotatable-region
  rendering mechanism) before implementation resumes on Phase 4.2 (unit
  layout) beyond what's already done (text/markdown/image field array +
  grid, see UnitFields.tsx) and Phase 4.3+ (span/relation UI, still
  unstarted). Do not implement further on this until the design questions
  above are resolved.

11f. RESOLVED + IMPLEMENTED (2026-09-18): layout constants, QuickJS-powered
  templating, `::tokenize` vs `::field`, and span answers including text

  Follow-up discussion after 11e, refining three things before moving on to
  relation UI:

  1. `::field[column]` was decoupled into two directives with distinct
     contracts: `::field[name]` (plain injection, optionally
     `{markdown=true}` for nested-markdown interpretation) vs.
     `::tokenize[name]` (annotatable rendering for span variables). Both
     directives resolve `name` against ONE shared namespace: unit data
     columns UNION the layout's new `constants` map (below) -- never a
     composed/rendered blob. `markdown=true` and `::tokenize` are NOT
     combinable on the same reference (rendered/stripped markdown text no
     longer lines up 1:1 with the raw string's character offsets) -- this
     is documented but not yet schema-enforced (still a manual-authoring
     footgun, tracked as a follow-up).

  2. `UnitLayoutSchema` gained `constants?: Record<string, string>`: named
     string constants versioned alongside the layout/codebook (not per-unit
     data), for two purposes: (a) literal/free text that needs to be
     `::tokenize`d without being tied to a real unit-data column -- keeping
     the "annotation offsets always resolve against ONE stable, versioned
     string" guarantee intact (a composed/rendered blob's contents could
     shift under a future template edit, which would silently corrupt
     stored offsets); (b) conditional layout content, e.g. showing
     different intro text to an experimental vs. control group.

  3. `{{...}}` template interpolation was upgraded from Phase 4.2's naive
     `{{column}}` regex substitution to full expression evaluation: each
     `{{ expression }}` block is now a real JS expression, evaluated in the
     SAME QuickJS sandbox as `condition` items (11d), against a merged
     context of unit data columns + this layout's `constants` + known
     variable values (highest precedence) -- enabling e.g.
     `{{is_experiment ? experiment_intro : control_intro}}`. Implementation:
     extracted a shared `evaluateExpression(expression, values)` helper
     (`codebook/expression.ts`, non-boolean-coercing) out of the old
     `conditions.ts`, which `evaluateCondition` now calls and
     `Boolean(...)`-coerces, and which the rewritten (now async)
     `renderTemplate.ts` also calls per `{{...}}` block, `String(...)`-
     coercing each result (`undefined`/errors render as empty string, same
     graceful-degradation behavior as before).
       Async-rendering architecture: since QuickJS evaluation is async but
     React rendering wants a synchronous string, template resolution moved
     OUT of `UnitFields` (a render-time component) and INTO
     `JobManager.resolveUnitLayout` -- called once per unit inside the
     already-async `advanceUnit` step-computation, alongside where
     `currentUnitLayout` was already being set. `UnitFields` therefore only
     ever receives an already-resolved, synchronous `layout.template` and
     stays a simple synchronous component; `::field`/`::tokenize`
     directives are deliberately NOT touched by `renderTemplate` (they
     still resolve directly against the raw data/constants lookup in
     `UnitFields`), preserving exact raw-string character offsets for spans.

  4. `SpanAnswerSchema` gained a `text: string` field: the exact substring
     of the target column/constant at `[offset, offset+length)`, captured
     by the client when the span is created (`SelectableText` slices the
     raw text; `SpanAnnotationContext.addSpan` now takes `(offset, length,
     code, text)`) and included in the submitted answer. Redundant with
     `field`+`offset`+`length` by construction, but saves downstream
     analysis from needing to re-fetch/re-slice the raw unit data just to
     know what text was actually annotated -- a small, deliberate bit of
     data duplication for convenience.

11d. RESOLVED: scripting/condition-expression sandbox choice (CEL vs JS)
  Context: `condition` items' `expression` field (§2) and any future
  codebook/layout scripting need a safe way to evaluate a small boolean/
  logic expression against known variable values, without giving codebook
  authors (who may not be trusted the same as job admins) unsandboxed
  access to the host JS environment. Phase 3 originally used a plain
  `new Function(...)` -- flagged as a real risk once written down
  explicitly (a hostile/broken expression could read host globals or, if
  ever evaluated server-side, affect other coders' sessions).

  Two real alternatives were evaluated (Phase 4.2, 2026-09-18ish):
    - CEL (Common Expression Language): briefly adopted via
      `@marcbachmann/cel-js` -- safe by construction (no loops/mutation/
      I/O by design), and the CEL *spec* itself is healthy (cel-go, now
      under the cel-expr org, 3.1k+ stars, active). BUT: cross-language
      support turned out much weaker than hoped for this project's
      multi-server-language ambitions (Python/R server backends,
      design plan §3/§6) -- `cel-js` bindings are small/niche (and a
      competing `ChromeGG/cel-js` package is already archived, confirming
      the worry that betting on CEL bindings outside Go is risky);
      cel-python is tiny; there is no CEL-R binding at all, and building
      one from scratch (e.g. via cel-cpp + Rcpp) was the only path.
    - QuickJS: real JavaScript, run inside a small, genuinely sandboxed
      WASM interpreter (separate heap, zero ambient host access unless
      explicitly bound in). JS is far more widely known than CEL by
      codebook authors. Cross-language story turned out to be *better*
      than CEL's, not worse: R already has a mature, actively-maintained
      CRAN package (`jeroen/V8`, real embedded Google V8, maintained by a
      trusted rOpenSci-affiliated author) for running real JS -- so no
      from-scratch language binding is needed for any target runtime.

  DECISION: switched to QuickJS (`quickjs-emscripten-core` +
  `@jitl/quickjs-wasmfile-release-sync`, a single lightweight release
  variant -- NOT the "batteries included" `quickjs-emscripten` package,
  which bundles four WASM variants and meaningfully bloats the client
  bundle). Rationale, in the user's own words: JS is more flexible and
  widely known; the R ecosystem story is trustworthy (Jeroen's package);
  and even if QuickJS itself ever loses relevance, QuickJS-authored
  scripts are still just plain JS and would run unmodified in any other
  JS engine (or a sandboxed sidecar) -- existing codebooks would not need
  to change. This also aligns with the project's general philosophy of
  provenance/reproducibility: JS is in no danger of disappearing.

  Implementation: `packages/client/src/lib/codebook/conditions.ts`
  (`evaluateCondition`, now async) loads a cached QuickJS WASM module once,
  JSON-embeds the (identifier-safe-filtered) variable-value context as
  `let` bindings in a generated code string, and evaluates
  `Boolean(<expression>)` via `QuickJS.evalCode(...)` with a 500ms
  interrupt deadline and a 1MB memory limit as belt-and-braces guards
  against runaway/hostile expressions. `codebook/tree.ts`'s
  `collectSteps`/`computeTopLevelSteps`/`computeLoopSteps` became async as
  a consequence (awaited from `JobManager`'s already-async
  `advanceTop`/`advanceUnit`, so no further public API changes were
  needed). `condition` items' `expression` field is plain JS
  (`===`, not CEL's `==`).

12. REACTIVE RECOMPUTATION OF CODEBOOK/LAYOUT STATE (variable-dependent
    scripts + values)                    [RESOLVED + IMPLEMENTED 2026-09-18]

  Problem: codebook items and unit layout content can both reference or
  embed QuickJS expressions/scripts that read *variable values* (e.g. a
  `condition` item's `expression`, later probably also question-text
  interpolation and unit-layout markdown content per §11c/§11's "inject
  fields via templating, possibly with scripts" history). Whenever a coder
  answers a variable, everything downstream that depends on that variable
  needs to be recomputed -- but nothing else should be needlessly
  recomputed. The old app tried to solve this with an explicit "trigger"
  system: a maintained graph of "changing variable X should re-run
  computations Y, Z". This is exactly the kind of bookkeeping that drifts
  out of sync with the actual script content over time (a script's real
  dependencies change, but nobody updates the trigger list) and was
  flagged (2026-09-18) as unnecessarily complicated for what we need.

  Proposed alternative: a single, well-defined "recompute pass" plus
  per-slot memoization, rather than a hand-maintained trigger graph:

  a. One function (name TBD, NOT `prepare_everything_and_run_quickjs`) is
     the sole entry point, e.g. `recomputeCodebookState(codebook, unit,
     values)`. It is called every time relevant state changes (i.e. after
     any variable is answered/changed -- job-level "user variable" values
     or per-unit "unit variable" values). It walks every "computed slot"
     in the current codebook/unit context (condition visibility today;
     eventually also layout/question-text script-interpolated content
     once §11c is resolved) and returns the up-to-date derived state
     (current steps, rendered layout, etc) that JobManager/UI consume.

  b. Dependency extraction, done once per script (e.g. at codebook-load
     time, not on every recompute): statically scan each embedded script/
     expression's source text for variable-name references, and record
     that as the slot's declared dependency set. This can be done cheaply
     and conservatively via a whole-word regex match of each *known*
     variable name against the script source (over-approximation is fine
     and safe here -- a false-positive dependency just causes an
     occasional unnecessary recompute, never a missed one; a real
     AST/identifier parse would be more precise but is not needed for
     correctness, only for slightly better cache-hit rates).

  c. Per-slot cache: for each computed slot (keyed by something stable,
     e.g. the item's `position` + expression/template source, or a
     content hash of the same), store (1) the last-seen values for just
     that slot's declared dependencies, and (2) the last computed result.
     On each recompute pass, for each slot: compare the current values of
     its declared dependencies to the cached snapshot (shallow per-key
     compare is enough, since variable values are small, wholesale-
     replaced objects, not mutated in place -- see VariableValueSchema);
     if unchanged, reuse the cached result without re-invoking QuickJS; if
     changed (or slot not yet cached), re-run the script/expression and
     update the cache.

  This keeps the mental model simple (one recompute pass, no manually-
  maintained trigger graph) while still avoiding needless repeated QuickJS
  evaluation. It generalizes the pattern `evaluateCondition`/
  `computeTopLevelSteps`/`computeLoopSteps` (§4/§11d) already use in a
  naive, fully-recompute-every-time form today -- fine for the current,
  trivially-sized demo codebook, but worth revisiting once condition
  counts and/or layout-embedded scripts grow.

  Status: IMPLEMENTED (2026-09-18), once §11 (unit-layout/markdown
  scripting design) landed, as one shared utility used by BOTH condition
  evaluation and unit-layout template interpolation, per the plan above:

    - `codebook/dependencies.ts`: `extractDependencies(script, knownNames)`
      -- the whole-word regex over known variable/value names described in
      (b) above, done fresh per call (cheap enough not to need its own
      separate caching layer).
    - `codebook/expressionCache.ts`: `ExpressionCache` -- the per-slot
      memoization described in (a)/(c): `evaluate(key, expression, values)`
      extracts `expression`'s dependencies against `Object.keys(values)`,
      shallow-`Object.is`-compares them to the last-cached snapshot for
      that `key`, and reuses the cached result on a match instead of
      re-invoking `evaluateExpression`/QuickJS.
    - `codebook/tree.ts`: `computeTopLevelSteps`/`computeLoopSteps` gained
      an optional trailing `cache?: ExpressionCache` parameter; each
      `condition` item is evaluated via `cache.evaluate("condition:" +
      position, ...)` when a cache is supplied, falling back to the
      original uncached `evaluateCondition` otherwise (so existing callers/
      tests that don't pass a cache are unaffected).
    - `codebook/renderTemplate.ts`: gained optional trailing `cache?`/
      `keyPrefix?` parameters; each `{{...}}` block is its own slot, keyed
      by `${keyPrefix}:${blockIndexInTemplate}` -- safe to key purely by
      index since a given layout's `template` string (and therefore its
      block order) never changes between calls, only the surrounding
      `values` do (which is exactly what should invalidate a slot).
    - `JobManager`: owns exactly ONE `ExpressionCache` instance per coder
      session (a private field), passed to every `computeTopLevelSteps`/
      `computeLoopSteps`/`resolveUnitLayout`->`renderTemplate` call.
      Notably required NO manual "clear on unit change" bookkeeping: since
      cache entries are invalidated purely by comparing declared
      dependency VALUES (not by unit/step identity), a template block
      referencing e.g. a per-unit `headline` column simply misses the
      cache once that unit changes -- the mechanism designed in (c) above
      handles this "for free".

  Verified via 3 new test files (`dependencies.test.ts`,
  `expressionCache.test.ts` -- using `vi.spyOn` on `evaluateExpression` to
  assert call counts under repeated/changed dependency values --, plus a
  cache-aware case added to `renderTemplate.test.ts`), full workspace
  typecheck/lint/build/test, and a live smoke test against a running
  mock-server instance (2 units, both with conditions/templates/spans/
  relations) confirming correctness is unaffected by the cache being
  active (i.e. this is a pure performance optimization, not a behavior
  change).
